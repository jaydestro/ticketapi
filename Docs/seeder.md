# Run Seeder

Seeder writes the repeatable ticketing workload used by the API and LoadGen. It creates 5,000
events and 250,000 orders with stable IDs and a fixed random distribution. Event
`event-00001` is the Championship Final and receives 42,000 orders so expensive query patterns
are easy to reproduce.

Seeder performs live bulk writes and consumes request units. Confirm the account, database, target
schema, and active identity before running it.

## Prerequisites

- .NET SDK 10.0.302 or later
- A root `appsettings.json`, normally generated by prompt 01
- An existing Cosmos DB database and permission to create containers and write items
- For Azure, an authenticated identity available to `DefaultAzureCredential`, such as `az login`

Builds copy the root `appsettings.json` beside the Seeder executable through
`Directory.Build.targets`. Run Seeder from the repository root so the commands and shared
configuration are easy to identify.

## Authentication and configuration

Seeder reads the `CosmosDb` section from the copied `appsettings.json`, followed by environment
variable overrides.

- When `CosmosDb:AccountEndpoint` is set, Seeder uses `DefaultAzureCredential`.
- Otherwise, Seeder uses `CosmosDb:ConnectionString`.
- A localhost connection string enables gateway mode and trusts the emulator's development
  certificate.
- If both values are set, `AccountEndpoint` takes precedence.

For a live Azure account with local Entra authentication, use an endpoint and leave the connection
string empty:

```json
{
  "CosmosDb": {
    "ConnectionString": "",
    "AccountEndpoint": "https://your-account.documents.azure.com:443/",
    "DatabaseName": "TicketingDb"
  }
}
```

The database should already exist in Azure. The built-in Cosmos DB Data Contributor role can
create and write containers but cannot create a database. Prompt 01 creates the database and grants
the required data-plane access before Seeder runs.

Use standard .NET configuration names for temporary environment overrides:

```powershell
$env:CosmosDb__AccountEndpoint = "https://your-account.documents.azure.com:443/"
$env:CosmosDb__DatabaseName = "TicketingDb"
```

## Seed the baseline schema

The default target is `legacy`, which is the schema created by prompts 01 and 02:

```powershell
dotnet run --project .\Seeder\Seeder.csproj
```

The explicit equivalent is:

```powershell
dotnet run --project .\Seeder\Seeder.csproj -- --target legacy
```

| Container setting | Default name | Partition key | Documents written |
| --- | --- | --- | ---: |
| `EventsContainerName` | `Events` | `/id` | 5,000 |
| `OrdersContainerName` | `Orders` | `/id` | 250,000 |

Seeder upserts deterministic IDs, so rerunning it does not increase document counts. Generated
dates are relative to the current run time, so reruns refresh timestamp fields as well as restoring
the generated event and order values.

## Seed the optimized After schema

Use the `after` target for the optimized source container and materialized read models:

```powershell
dotnet run --project .\Seeder\Seeder.csproj -- --target after
```

| Container setting | Default name | Partition key | Documents written |
| --- | --- | --- | ---: |
| `TicketingContainerName` | `ticketing-write` | `/eventId` | 255,000 source documents |
| `EventsByCityContainerName` | `events-by-city` | `/cityKey` | 5,000 projections plus one backfill marker |
| `OrdersByCustomerContainerName` | `orders-by-customer` | `/customerId` | 250,000 projections |
| `LeaseContainerName` | `change-feed-leases` | `/id` | None by Seeder |

A normal After run reports 510,001 writes: 255,000 source documents, 255,000 projections, and the
backfill marker. The change-feed worker uses the lease container after the API starts.

### Reset the After containers

`--reset` deletes and recreates all four After containers before seeding:

```powershell
dotnet run --project .\Seeder\Seeder.csproj -- --target after --reset
```

This is destructive. It deletes source data, projections, leases, and change-feed progress. The
switch has no effect on the legacy target; do not use it as a way to reset `Events` or `Orders`.

### Rebuild only the read models

Use `--projections-only` to upsert the event-by-city and order-by-customer projections without
writing source documents:

```powershell
dotnet run --project .\Seeder\Seeder.csproj -- --target after --projections-only
```

The source documents must already exist. This mode writes 255,001 documents, including the
backfill marker.

Do not combine `--reset` and `--projections-only` unless an empty `ticketing-write` container is
intentional. Reset deletes the source container, and projections-only does not refill it.

## Progress and completion output

Seeder enables Cosmos bulk execution, writes in chunks of 200, and prints progress every 10,000
successful upserts. The client retries rate-limited requests up to 100 times with a maximum
cumulative retry wait of 30 minutes.

A successful run ends with:

```text
=== Seed complete ===
Documents written: ...
Total RU consumed: ...
Wall-clock time:   ...
```

Seeder does not write a separate log file. Redirect terminal output when a retained run record is
needed:

```powershell
dotnet run --project .\Seeder\Seeder.csproj 2>&1 | Tee-Object .\logs\seeder.log
```

An unhandled Cosmos or authentication error stops the run with a nonzero exit code. Do not treat a
partial run as complete; fix the underlying configuration, RBAC, network, or throttling problem and
rerun the same upsert command.

## Command reference

```text
Seeder [--target legacy|after] [--reset] [--projections-only]
```

| Option | Behavior |
| --- | --- |
| `--target legacy` | Seed the baseline `Events` and `Orders` containers. This is the default. |
| `--target after` | Seed the optimized source container and read models. |
| `--reset` | Delete and recreate the four After containers before writing. |
| `--projections-only` | Write only After read models and the backfill marker. Requires `--target after`. |

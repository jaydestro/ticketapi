# Contributing

Thanks for your interest in this project. It is a demonstration repository: it builds a live
event ticketing API on Azure Cosmos DB through a numbered sequence of prompts, then measures
the result. Contributions that keep that workflow reproducible are welcome.

## What lives in this repository

Only reusable workflow assets are committed:

- `Docs/prompts/` - the numbered prompts that drive the build
- `Docs/loadgen.md` - how to run the workload generator
- `examples/` - captured prompt 03 output for the before/after comparison
- `Seeder/` - deterministic data generator
- `LoadGen/` - workload generator and RU comparison harness
- `scripts/` - PowerShell launchers
- `appsettings.json.example` and `Directory.Build.targets` - shared configuration

The following are produced by running the workflow and must **not** be committed:

- `TicketingApi/` and any generated test project - output of prompt 03
- `appsettings.json` - generated by prompt 01, contains environment-specific values
- `infra/` - generated Bicep
- `.azure/`, `bin/`, `obj/`
- `.agents/`, `.claude/`, `skills-lock.json` - locally installed agent skills

Keeping generated output out of Git is what allows the same prompts to be re-run and compared.
Please check `git status` before committing and never stage a generated API or test project.

The one exception is `examples/`, which holds deliberate snapshots of prompt 03 output copied
there to document the before/after comparison. See [examples/README.md](examples/README.md).

## Prerequisites

- .NET SDK 10.0.302 or later (projects target `net10.0`)
- PowerShell 7 for the scripts in `scripts/`
- An Azure account able to create an Azure Cosmos DB for NoSQL account, if you intend to run
  the workflow end to end. See [Docs/prompts/01-create-cosmos-entra.md](Docs/prompts/01-create-cosmos-entra.md).

The Azure Cosmos DB emulator is not a substitute: it does not report request-unit charges the
way the service does, and the comparison workflow depends on RU measurements.

## Making a change

1. Create a branch off `main`.
2. Make the change.
3. Build the projects you touched:

   ```powershell
   dotnet build .\LoadGen\LoadGen.csproj
   dotnet build .\Seeder\Seeder.csproj
   ```

4. If you changed a PowerShell script, confirm it parses:

   ```powershell
   $errors = $null
   [System.Management.Automation.Language.Parser]::ParseFile(
       (Resolve-Path .\scripts\run-loadgen.ps1), [ref]$null, [ref]$errors)
   $errors
   ```

5. Confirm `git status` shows only the files you intended to change.
6. Open a pull request describing what changed and how you verified it.

## Changing the prompts

The prompts deliberately describe *what* to build rather than *how*. That latitude is the
point: the same prompts are run with and without additional design guidance so the results can
be compared. When editing a prompt, avoid encoding a specific implementation or fix into it
unless that is the explicit goal of the change.

State prerequisites in two places so they are visible either way: the prose section of the
document, and inside the prompt text that gets copied.

## Measuring a change

If a change is meant to affect Cosmos DB cost or latency, include a LoadGen comparison. Keep
the workload, seed, concurrency, and report interval identical between the two runs:

```powershell
.\scripts\run-loadgen.ps1 -Workload Read -Concurrency 10 -Seed 42 -ReportInterval 0.5
```

The default Read workload is read-only, so it will not modify seeded data.

## Reporting problems

Open an issue using the template and include the prompt stage you were on, what you expected,
and what happened. Never paste account keys, connection strings, tokens, or subscription
identifiers into an issue.
